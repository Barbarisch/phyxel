# Feedback inbox

Lessons-learned and feature-requests captured during Phyxel **game-dev** sessions, appended by
`phyxel feedback` (usually via the `/feedback` command). **Engine-dev** sessions consume this
via `/triage-feedback`: summarize, fold actionable items into `docs/AgentContext.md`'s roadmap,
then move handled entries to `archive.md`.

Entry format:

    ## <date> — <project> — <bug|gotcha|feature-request>
    <description>

## 2026-07-12 — Emberwake — feature-request
Axe tool item + chopping/gathering swing animation. Survival/RPG gathering needs a real axe item (equippable via RpgItem/EquipmentSystem) plus a chop/swing animation family (like melee_anim_families) so chopping a tree for wood is an actual swing with wind-up + impact, not an instant voxel break. ## 2026-07-12 — Emberwake — feature-request
Satisfying tree/object destruction - a chopped tree should topple and fall, not vanish. When a tree is chopped through, it should physically fall over (coherent-fragment destruction via the GPU AVBD / VoxelDynamicsWorld bonds-to-weld path) and settle as gatherable logs/debris. Applies to destructible objects broadly; survival wood-gathering is the driving case, so felling reads as a real event.

## 2026-07-12 — Emberwake — feature-request — ✅ RESOLVED 2026-07-13
API to fire a declarative trigger's 'when' event on demand AND query the current shell screen state (playing / victory / game_over / menu / pause). Lets the game-production tracker runtime-validate win_condition/lose_condition (the trigger actually fires -> the victory/game-over screen shows) without a human. Ties into the triggers[] {when,then} system (TriggerSystem) + the ScreenState shell. Pairs with the logged input-injection request.
> RESOLVED: shipped `POST /api/triggers/fire` + `fire_trigger` MCP tool (mode `id` = run that trigger's then-actions immediately via the host executor, synchronous+observable; mode `event` = replay the real when->then path) and `GET /api/screen/state` + `get_screen_state` MCP tool. Built with the EXISTING public `TriggerSystem::listTriggers()` + `executeHostAction()` — no TriggerSystem change. IMPORTANT ARCHITECTURAL NOTE: the editor process (which serves the API) has NO standalone-shell GameScreen/ScreenState, and show_victory/show_credits NO-OP in the editor host (they only render in a packaged game's shell) — so get_screen_state is SYNTHESIZED from scene-type + pause + visible non-HUD menus (HUD overlays like hud_health are excluded, else play reads as menu). Win via transition_scene IS editor-observable; win via show_victory is confirmable only by the executed-action list, not a rendered screen. Validators production_runtime.rv_win_condition/rv_lose_condition (L3) fire the trigger + observe; live-verified on Emberwake (executed [complete_objective, show_victory] / [fail_objective]). Files: editor/src/Application.cpp (fire_trigger + get_screen_state handlers), engine/src/core/EngineAPIServer.cpp (routes), scripts/mcp/phyxel_mcp_server.py (tools), scripts/mcp/production_runtime.py (validators). REMAINING: a true win_condition L4 (playtest reaches victory in the PACKAGED shell) still needs the shell to host the API OR an input-injected shell playthrough.

## 2026-07-12 — Emberwake — feature-request — ✅ RESOLVED 2026-07-13 (reused existing NavGrid)
Expose the structure-gen TraversalProbe (character-box reachability) at whole-GAME/level scale via the API: given the loaded game, is the win/goal state reachable from the start AND from representative mid-game states (softlock / completability check). Underpins the game-production Phase 7 completability validator (an all-green milestone checklist can still be an unwinnable game). Also useful: resource-loop-closure for survival (no needed consumable without a reachable source).
> RESOLVED: game-scale reachability was ALREADY served by `GET /api/navgrid/path?x1=&z1=&x2=&z2=` (NavGrid + AStarPathfinder, world-scale, wired to the live world, returns {found, waypoints}). TraversalProbe (engine/{include,src}/core/TraversalProbe.*) is micro-resolution + structure-scoped (4M-visited cap) — NOT the right tool for whole-level reachability; NavGrid is. Added `production_runtime.rv_level_playability` (L3): confirms the player spawns on a walkable NavGrid cell AND (when the win is location-based — an entity_reached_region trigger) paths spawn->goal via /api/navgrid/path. Live-verified on Emberwake: spawn (16,16) walkable; goal (22,22) reachable (2 waypoints); unreachable goal (9002,9002) → honest "possible softlock" (ok=False), NOT a false pass. CAVEATS to remember: NavGrid clamps to 512×512 columns around loaded chunks (NPCManager::buildNavGrid, kMaxNavHalfExtent=256) so far-apart spawn/goal fall outside; and NavGrid MAX_STEP_UP=0 (+ jump-links) is more conservative than the player's real 0.44m step-up, so "not reachable" is a signal to inspect, not proof. A true TraversalProbe-at-scale (micro-accurate, backed by live VoxelDynamicsWorld occupancy) is only worth building if NavGrid's fidelity proves insufficient. Also NOT done: resource-loop-closure (survival source/sink graph).

## 2026-07-13 — game-production — feature-request (testing fidelity gap) — ✅ FOUNDATION BUILT 2026-07-13
Let the PACKAGED STANDALONE game shell optionally host the EngineAPIServer (behind a `--test`/`--api` launch flag), so automated game-production validators can drive + observe the ACTUAL shipped game, not the editor proxy.
> BUILT (core + fidelity win verified): `engine/{include,src}/core/GameApiService.*` — a self-contained reusable API host wiring the ~10 harness endpoints against NON-OWNING pointers to a game's own subsystems (renderCoordinator/npcManager/triggers/screen/entityRegistry/player + EngineRuntime for InputManager/perf/scene). Hosted by GameShell (`startTestApi`/`pumpTestApi`/`stopTestApi` + `api*` virtual hooks the game overrides); `EngineConfig.testApiEnabled` default false; generated `main.cpp` enables it only for `--test [port]`, binds localhost. NO editor changes. VERIFIED end-to-end: generated ApiTestGame from testing_baseline.json, built the standalone (add_subdirectory phyxel_core), ran `--test 8091` — API hosts on the REAL packaged game, `get_screen_state` returns the REAL GameScreen state ("intro" with visible_menus [intro:main], source "shell") which the editor CANNOT (editor synthesizes + show_victory no-ops); real entities+UUIDs, inject_input, player_state all work. FOLLOW-UPS to fully automate an in-Playing playthrough: (1) a `ui_click` endpoint — menus don't consume injected InputManager keys, so intro→Playing needs a menu button click; (2) build the NavGrid in the standalone (navgrid_* report "not available" until npcManager_->buildNavGrid()); (3) populate PerformanceMonitor in EngineRuntime (fps reads 0 on intro — is EngineRuntime updating it each frame?). Files: engine/include/core/GameApiService.h, engine/src/core/GameApiService.cpp, engine/include/core/GameShell.h, engine/src/core/GameShell.cpp, engine/include/core/EngineConfig.h, tools/create_project.py. Full write-up: docs/game-production/README.md §6.6. Today only the editor process (`editor/src/Application.cpp`) instantiates `EngineAPIServer`; the standalone shell (`package_game.py` output, `EngineRuntime`/generated game class) runs no API server, so ALL runtime validation happens in `phyxel.exe --project` (editor host). That harness is high-fidelity for engine systems (world/render, player control via input-injection, FPS, NavGrid reachability, physics, trigger *wiring*) but diverges from real play where it matters most: in the editor `show_victory`/`show_credits` NO-OP (shell-only), there is no `GameScreen`/`ScreenState` (get_screen_state is synthesized), and injected input must bypass the ImGui keyboard-focus gate. Consequence: the shell screen-state FLOW (intro → menu → play → victory/game_over → credits) is un-observable in the editor, so `intro`/`victory_screen`/`game_over_screen`/menu-navigation and a TRUE `win_condition` L4 currently require a human packaged-shell playtest and their validators honestly cap at L3. Adding the shell API-host flag would (1) raise those L3 caps to genuine L4 against real play conditions and (2) let the Phase 7 adversarial fresh-agent playtest run against the actual shipped build. Design care: gate the flag so shipped players can't accidentally expose it (dev/test builds only, or require an explicit env var + localhost bind). Full write-up: docs/game-production/README.md §6.6.
