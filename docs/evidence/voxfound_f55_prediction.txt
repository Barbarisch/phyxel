F5.5a -- THE DISPATCH FLOOR (written before the code)

WHAT IT BUILDS
  The GPU tick records, per tick: 13 single passes + 32 Jones-Plassmann colour rounds + 8 iterations x (32 primal
  colours + 1 dual) = 309 dispatches, each followed by a full barrier, whether a colour has bodies or not. F5.2b
  measured 8.1 ms per tick with 7 bodies all asleep: the floor is the dispatches, not the work.
  Lever: FUSE. One extra pipeline from the same source (voxfound_bodies_fused.comp, local size 1024) runs the colour
  rounds AND all iterations of {primal per colour, dual} in ONE dispatch of ONE workgroup, separated by workgroup
  barriers (barrier() + memoryBarrierBuffer()); threads stride over bodies / constraints when there are more than
  1024. Colour rounds stop as soon as no body is left uncoloured; the primal loops only over the colours used
  ("dispatch only the colours used"). Asleep bodies already get no colour (dynamicBody), so the primal skips them
  ("skip sleepers"). The per-pass code is moved into functions shared by both pipelines, unchanged.
  Ticks per dispatch: 13 + 1 = 14 dispatches per tick instead of 309. A switch BodySimGpu::setFused(bool) keeps the
  old path as the control. Default: fused.

PREDICTIONS (headless, Vulkan integration tests, VoxFoundBodySimGpuTest; GPU sharing stated at run time)
  A1 identical results: on the R8b blast (stone wall E/T 80, 8000 N s, 900 ticks) the fused path's poses are
     BIT-EQUAL to the per-colour path's at every 30-tick sample (same float operations in the same order; the colour
     a body takes is the same because a round's read of a neighbour coloured in the same round is already treated
     as a competitor). RISK named: the driver compiles the moved code in a different module and may contract
     multiply-adds differently; if A1 fails on that, the fallback gate is: every F5.2b rig assertion still passes,

  A2 every existing GPU rig test (R1-R8b, G1-G4) passes with fused as the default, unchanged thresholds.
  A3 the ladder: the large wall (256 x 128 x 4, base fixed, hit at the centre) at E/T 250 / 650 / 2800 gives about
     100 / 300 / 1,000 bodies (F5.1 measured 59 at 150, 468 at 1000, 947 at 2500). Each runs 300 ticks from the break
     (pieces fly and land), on both paths:
       nothing overflows (scratch, constraints), every dynamic body coloured, no body through the ground, poses

F5.5a2 -- THE NARROWPHASE IN PARALLEL (written 2026-11-18 after F5.5a's results, BEFORE any F5.5a2 code)

WHAT IT BUILDS (the per-pass profile's two hot passes, K_PAIRS and K_HARD_BODY)
  - An awake list (compacted). Pairs are found per AWAKE body a against every other body j, kept when j is not
    dynamic or j > a -- each unordered pair once, the same set and the same (a, b) roles as today's j > i loop; an
    all-asleep scene finds no pairs at all instead of n^2 / 2 AABB tests.
  - K_NARROW: one 64-thread workgroup per pair (persistent groups striding the pair list). The pair's corner list
    (side 0 then side 1, corner order) is split in contiguous chunks; each thread counts its candidates, a workgroup
    scan gives offsets, and each thread writes its candidates at their offsets -- the SAME candidate order as the
    serial loop, so the cap (bucket winners, depth sort, spread picks with first-index ties) picks the same contacts.
    The cap's bucket winners run one thread per bucket; each spread pick is a workgroup argmax (first index on ties).
  - Hard contact, body-body: pairs found the same way at the post-solve poses (margin 0); one workgroup per pair takes
    the deepest point (first in serial order on ties) and stores it; each body then sums its share over j ascending
    exactly as today, reading the stored result instead of recomputing the voxel test (and each pair is tested once,
    not twice).
  - A switch setNarrowParallel(bool) keeps today's passes as the control. Default: parallel.
  Not changed here: K_WORLD and HARD_APPLY's world test (2.6 / 2.4 ms mean at ~1,000) and the candidate scratch per
  body (336 MB at 1,025) -- stated, next levers.

PREDICTIONS (headless, VoxFoundBodySimGpuTest; GPU sharing stated at run time)
  B1 identical results: the R8b blast (900 ticks) and every ladder rung (300 ticks) BIT-EQUAL between the parallel
     and the serial narrowphase at every 30-tick sample, and every counter equal (contacts, candidates, capped, pairs
     tested, hard fires). (Same named risk as A1: the driver compiling moved code differently.)
  B2 every GPU rig test passes unchanged (36/36 VoxFound GPU).

F5.5 TUNNELLING -- a fast piece through the ground (written 2026-11-18 BEFORE the fix's code)

THE BUG (found by F55aLadder at E/T 2800): the contact rule (F5.2a's escape, shared by the CPU reference and the GPU)
looks only at a corner's 26 neighbour cells. A corner more than one voxel inside solid has no empty neighbour: "deep",
counted, NO contact, no hard-contact push. A piece moving faster than ~1 voxel per tick (7.5 m/s at 1/8 m, 60 Hz) can
put every corner deeper than that into y < 0 in one tick and then falls for ever. The same speed can carry a corner
clean over a 1-voxel slab (it ends in air below it: no contact at all).

THE FIX (CPU reference and GPU, the same rule): a corner that moved >= 1 voxel this tick (tick-start pose -> current
pose) and got no contact from the escape gets a SWEPT contact: march its path through the world grid from the tick-
start position (3D DDA, ties to the lowest axis) and take the first solid cell entered: normal = that face's outward
normal, depth = how far the current position is past that face's plane, the face's neighbour index as the feature.
A path that starts inside solid, or enters none, gives nothing (as today). Bodies against bodies are unchanged (pieces
are thick enough; counted as deep as today). Measuring functions (penetration reports) do not sweep.

PREDICTIONS
  T1 (CPU reference and GPU): a 1-voxel and a 2x2x2-voxel stone body, 2 m above the ground, thrown straight down at
     15, 30 and 60 m/s: after 120 ticks every one rests on the ground (lowest corner >= -0.01 m, speed < 0.1 m/s).
     RED today: at 15 m/s and up they end below -0.5 m. Control: at 5 m/s (< 1 voxel per tick) the same result before
     and after the fix (the sweep never runs: lowest corner and pose equal to the red run's numbers).
  T2 (CPU and GPU): a 1-voxel-thick stone slab 1 m above the ground (world grid), a 2x2x2 body 1 m above it thrown down at
     30 m/s: it rests ON the slab (lowest corner >= 1.125 - 0.01 m). RED today: it ends below the slab.
  T3 the F5.5a ladder at E/T 2800: 0 bodies through the ground (1 today).
  T4 no regression: every VoxFound body test passes (CPU VoxFoundBody*, GPU VoxFound*Gpu*); F5.5a's and F5.5a2's
     bit-equalities still hold (both GPU paths share the rule).
  T5 cost: the ladder's per-tick cost within 10 % of F5.5a2's (10.4 ms at 1,025): only fast corners sweep.

  CORRECTION (still before code): no body has 1 voxel (pieces under 4 voxels are crumbs, crumbVoxels = 4), so T1's
     small body is the smallest one, a 1 x 1 x 4 rod lying along z -- the size of the piece that tunnelled.
WHAT WOULD COUNT AS A MISS
  any T1/T2 body below its surface; a body through the ground on the ladder; any regression; cost above +10 %.

F5.5a4 -- THE PRIMAL IN PARALLEL (written 2026-11-18 BEFORE its code; the split profile measured first,
voxfound_f55a4_profile.txt: at 1,025 bodies the solve is colour 0.16 + PRIMAL 3.48 + dual 0.04 ms per tick)

WHY: each colour's dispatch waits for its slowest body, and a big piece with hundreds of contacts sums them in one
thread, 8 iterations x its colour.
WHAT IT BUILDS: after the colour rounds (the fused one-dispatch colouring, bit-equal to the per-colour rounds), a
counting sort puts each colour's bodies in a list and writes an indirect dispatch per colour (empty colours dispatch no
groups). Each body's primal runs on one 64-thread workgroup: the threads take its constraints strided, sum partial
6x6 + 6 terms, a fixed tree reduction adds the partials, one thread adds the inertial terms and solves. The fused path
is not used with it. setPrimalParallel(false) keeps the serial primal as the control.
NOT BIT-EQUAL to the serial primal, stated before the run: the sum is reassociated (partials + a tree), so float
rounding differs and pile trajectories diverge chaotically. The gate is therefore the F5.2 one: determinism and every
rig's assertions.
