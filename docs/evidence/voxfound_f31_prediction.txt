F3.1 -- edit cost (VoxelFoundationPlan §9b). Written 2026-11-16, BEFORE any code.

The F3 row's first half: "edit cost per block << today's 2-13 ms chunk rebuild". Read as F2.16 read it: >= 3x below
the low end, so a 1 m brush (one block) costs <= 0.67 ms on the main thread from the request to the drawn lists
ready (RegionEdit::apply + RegionEdit::assemble), plus the next frame's upload (F2.17: 0.16-0.18 ms, unchanged here).

Where a 1 m edit's time goes today (F2.16 gate, CPU executor, median of 33 live edits; voxfound_f216_gate_edits.jsonl):
  rows 3.81 ms, connectivity 0.61, plan 0.07, clusters 0.06, sprigs 0.01, set 0.01 -> rebuild 4.50; assemble 2.43.
  1 voxel: rebuild 1.04 (connectivity 0.77, rows 0.23), assemble 2.48. 4 m: rebuild 47.8 (rows 46.9), assemble 2.48.

Changes (each exact by construction; the existing IncrementalRebuildEqualsAFullRebuild keeps pinning faces, groups,
cells, sprigs, blocking and connectivity after every one of 300 edits):
1. Rows: meshRunsPlan evaluates the face mask LAZILY. A face is added only if its run meets the footprint grown by
   one in u ([uLo-1, uHi+1]), so per row only the runs that touch that window are found (scan out from the window to
   where the material changes), and the head / stack tests read only the cells [u-1, u+w] of the rows they test
   (same rows m0..m1 as today). Today every row is evaluated over the whole slice width (256 cells).
2. Connectivity: updateBlockBlocking reports whether any block's "blocks sight" bit changed; no change -> the flood
   is skipped (connectivity is a function of the bits alone). When it runs, it is a bit-parallel flood (one 64-bit
   word per (x, y) row of blocks, dilate by shifts, AND with the open blocks, to a fixed point), per entry face.
3. Assemble: only the rebuilt chunks' lists are built (cellsOfGroups etc.); the pool update writes their spans; the
   Preview's drawn arrays are updated IN PLACE over the dirty ranges instead of copying the whole level image
   (selectLevel); the sprigs of the rebuilt chunks are spliced in. A full layout (first call, overflow) still copies
   everything.

Red tests first (deterministic work counters, not wall time; then wall time live):
- CPU VoxFoundMesher.RowRebuildReadsOnlyNearTheFootprint: engine terrain (buildTerrainArea, Perlin s7, 32 x 32 m
  area, 1/8 m), 60 random 1 m brush edits on and near the ground: cells evaluated <= 10 % of today's whole-width rows
  (today = rows x slice width), and the delta equals meshRunsDelta's (faces as a set). Red on today's executor.
- CPU VoxFoundMesher.ConnectivityFloodRunsOnlyWhenABlockingBitChanges + the bit flood equal to a reference stack
  flood on random blocking at 32^3 and odd sizes (densities 0-100 %). Red: no change report exists.
- CPU VoxFoundMesher.RegionEditAssemblesOnlyWhatChanged: a 2-chunk RegionEdit (CPU
  meshRuns + foliageSprigs as the builder output), 40 random edits incl. across the border: after each, the Preview's
  drawn arrays = a full assemble of the same store, and the bytes copied into the Preview <= the rebuilt chunks'
  lists + dirty ranges (today: the whole image every time). Red on today's assemble.

---- 2026-11-16 interim: two gate runs, then the p90 (written before the code below) ----
Run 1 (bit-row flood): 1 m request to lists ready median 0.53 / p90 1.15 ms; run 2 (the stack flood back: the bit flood
cost the same per flood, 0.184 vs 0.185 ms): 0.62 / 1.28 ms. Median under the 0.67 gate in both, by 8-20 %, while the
SAME legacy work varied up to 4x between the runs (legacy 1-voxel connectivity 0.18 vs 0.76 ms): not a margin to call
"<<". The p90 has two named causes in the per-edit rows: (a) assemble p90 0.74-0.85 ms = the sprig rewrite from the
first chunk whose sprig count changed to the end (~1.4 MB); (b) the flood, 0.2-0.5 ms when a blocking bit changed.
Change:
(a) sprig spans: each chunk's sprigs get a span with slack (count + a quarter, at least 64) in Preview::sprigs; gaps
    are never drawn (the renderer draws each chunk's [firstSprig, firstSprig + sprigCount)); a count that fits its span
    is rewritten in place, one that does not re-places every span (rare, like the face pool).
(b) the flood with flat block indices, a byte "seen" array and an index stack kept between calls (no allocation, no
    vector of ivec3).
Red: RegionEditAssemblesOnlyWhatChanged tightened -- bytes written <= the dirty ranges + the REBUILT chunks' sprig
spans (today: from the first shifted chunk to the end).
Predictions: assemble p90 <= 0.3 ms (1 m); flood <= 0.1 ms per flood; 1 m request to lists ready median 0.25-0.5,
p90 <= 0.67 ms. Pixels / exactness as before.
Red-to-green note: the first sprig-span build re-placed every span 5 times in the test's 40 edits (limit written
before the run: <= 4) with a fixed quarter of slack. Changed to the face pool's rule (slack x1.5 after each overflow),
the limit kept.
