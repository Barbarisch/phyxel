C3.3 — FAR-CHUNK DRAW PATH: FIRST PIXELS FROM PERSISTED LOD, AND THE PERF DEFECT IT EXPOSED
Date 2026-07-31. Release build. World: PhyxelProjects/FarLodTest.

THE WORLD (built for this, because no existing world could exercise the path):
  Streaming Perlin, seed 424243, loadRadius 3 / unloadRadius 4 (load 96 / unload 160 units),
  render distance 2048. That gap is the ONLY condition under which the far path does anything:
  a baked world keeps every chunk resident and it is a no-op by construction (LodBench gave
  far_chunks = 0 for exactly this reason).
  Structures: 5 rooms placed by the ENGINE's own generator via POST /api/structure/build
  ("placed":212 each) -- NOT hand-placed voxels.

FINDING 1 -- STREAMING WORLDS DO NOT SAVE GENERATED CHUNKS.
A "dirty" save on the freshly-streamed world wrote NOTHING: chunk_blobs = 0, so C3.2's hook on
saveChunk never fired and no pyramid existed. Generated terrain is regenerable from the seed, so
it is never dirty. Pyramids therefore only exist for chunks something EDITED -- which is exactly
C3.4's policy, but it means the far path shows edited/structure chunks only, never plain terrain.
That is a design consequence worth knowing, not a bug.

FINDING 2 -- C3.2 + C3.4 PROVEN END-TO-END IN A RUNNING ENGINE (first time).
After placing the 5 rooms and saving, queried the DB directly:
    chunk_blobs = 16    chunk_lod_blobs = 25 rows over 5 chunks, 12627 bytes
16 chunks saved; only the 5 carrying structures got pyramids. Plain terrain was correctly
skipped. Levels 1-5 present per chunk, e.g. (0,1,1): 1472 / 761 / 343 / 120 / 55 bytes.

FINDING 3 -- C3.3 DRAWS. THIS IS THE PROOF C3 EXISTED FOR.
Camera (420,260,420) yaw -135 pitch -28, read back from GET /api/camera. At that pose everything
in view is NON-RESIDENT (the structures are ~400 units away; unload distance is 160).
    far_lod OFF: far_chunks 0  -> screenshots/screenshot_20260731_164553_950.png = EMPTY SKY
    far_lod ON : far_chunks 5, far_instances 1262, stable across 3 polls
                 -> screenshots/screenshot_20260731_164639_168.png = terrain + structures VISIBLE
Geometry appeared where there was nothing, drawn from the persisted pyramid for chunks the
engine had unloaded. far_chunks = 5 matches the 5 chunks with pyramids exactly.

FINDING 4 -- AND IT COST 638 -> 2 FPS. A REAL DEFECT, MEASURED, NOT THEORISED.
The same screenshots carry the FPS counter: 638 with the path off, 2 with it on.
CAUSE: reach was derived from chunkInclusionDistance (3072 / 32 = 96), making the scan
193^3 = 7.2 MILLION chunk lookups PER FRAME, each also linearly scanning m_farLod.
FIX WRITTEN: cap reach at 12 chunks (25^3 = 15,625 probes) AND rescan only when the camera
CROSSES into a new chunk, so a stationary camera costs nothing. Eviction still runs every frame,
because a chunk becoming resident must stop being drawn immediately or it double-draws.

*** THE FIX IS NOT VERIFIED AT RUNTIME. ***
It compiles (Release). The re-test raced the engine's boot (curl exit 7 = connection refused) and
I ran out of session before re-running it. So the 638 -> 2 FPS regression is MEASURED and the
repair is UNMEASURED. Do not assume the fix works; re-run the A/B above and read the FPS counter.
Note for whoever does: STOP the engine before rebuilding -- the linker cannot overwrite a running
phyxel.exe, and I wasted a cycle testing a stale binary whose timestamp predated the fix.

============================================================================
FOLLOW-UP — THE FPS FIX IS VERIFIED, AND IT COST COVERAGE
============================================================================
Re-ran the identical A/B on the FIXED Release binary (built 16:50:55, after the fix was written;
engine stopped first this time so the linker could actually replace the exe). Pose read back
from GET /api/camera: (420,260,420) yaw -135 pitch -28, render distance 2048, daynight pinned.
FPS read by cropping the status bar of each screenshot, not from memory:

    BEFORE the fix:  far_lod OFF 638 FPS  ->  ON   2 FPS     (7.2M chunk probes per frame)
    AFTER  the fix:  far_lod OFF 626 FPS  ->  ON 624 FPS     (~0.3%, inside noise)
    screenshots/screenshot_20260731_171854_457.png (OFF) / _171913_793.png (ON)

So the 300x collapse is GONE. Bounding reach and rescanning only on a chunk crossing fixed it.

BUT THE FIX TRADED REACH FOR COST, and the same run shows it:
    far_chunks 5 -> 1  at the identical pose.
The camera sits in chunk (13,8,13); the structure chunks are at (0,1,0), (1,1,0), (0,1,1),
(1,1,1), (-2,1,0), (0,1,-2), i.e. Chebyshev distances 13, 13, 13, 12, 15, 15 chunks. kMaxFarReach
= 12 admits only (1,1,1), the one at distance 12.
  [CORRECTION, solution-auditor: this list first said (1,1,0) was distance 12. It is 13. The
   conclusion is unchanged -- it is excluded either way -- but a wrong number in an evidence
   file is exactly what this project has been burned by, so it is corrected in place, not
   silently edited.] So the FPS number above is measured while drawing ONE
far chunk, not five -- honest note: it is not a perfectly matched comparison to the old 5-chunk
ON case. The collapse was SCAN-driven (7.2M probes/frame regardless of how many chunks drew), so
the fix addresses the real cause, but the perf figure should be re-taken once coverage is restored.

SHARPER CAUSE than I first stated (solution-auditor, from reading the pre-fix control flow):
once the 5 chunks were already in m_farLod, the `already` check meant `built` never incremented,
so the `built < s_farLodBudgetPerFrame` early-exit COULD NEVER FIRE. The full 7.19M-probe scan
therefore ran on EVERY frame, not merely on the first. That is why it was 2 FPS rather than one
bad frame followed by recovery.

REMAINING GAP, stated rather than closed: post-fix far_instances was never logged and the ON run
drew 1 chunk, so "626 -> 624" is not a matched 5-vs-5 measurement. The scan-vs-draw attribution
is supported by the control flow above, but the magnitude comparison is partly inferred.

THE RIGHT FIX, not taken here: do not scan a volume at all. Ask storage which chunks HAVE
pyramids within range and iterate THAT set -- it is tiny (5 chunks in this world) versus 25^3 =
15,625 speculative probes, and it removes the reach cap entirely, so coverage stops depending on
an arbitrary constant. That needs a new WorldStorage query (list chunk coords with LOD rows) and
was not attempted.

============================================================================
FALSIFICATION — THE GEOMETRY REALLY DOES COME FROM chunk_lod_blobs
============================================================================
Everything before this showed geometry APPEARING when far_lod was enabled, which only proves the
toggle does something -- not that the pixels came from the persisted pyramid rather than some
other path. This is the test that distinguishes them: delete the rows and see if it disappears.

Identical pose both runs, read back from GET /api/camera: (300,220,300) yaw -135 pitch -30,
render distance 2048, far_lod ON in BOTH runs. The ONLY variable changed is the DELETE.

  chunk_lod_blobs = 25 rows:  far_chunks 5, far_instances 4876, FPS 555
        screenshots/screenshot_20260731_174529_698.png -- terrain island + structures VISIBLE
  DELETE FROM chunk_lod_blobs (0 rows; chunk_blobs left INTACT at 16, verified):
                              far_chunks 0, far_instances 0,    FPS 639
        screenshots/screenshot_20260731_174719_016.png -- EMPTY SKY

Both runs report the same world state otherwise: Chunks(104), Placed Objects(6), structure(6).
So the voxels still exist and the chunks still stream; only the coarse rows are gone, and the
far geometry goes with them. The rendered pixels are sourced from the persisted pyramid.

*** CORRECTION -- THE RESTORE FAILED, AND MY FIRST WRITE-UP OF IT WAS WRONG. ***
This file originally said "the DB was restored from a copy taken before the delete; lod rows back
to 25." That is FALSE and is corrected here rather than silently edited.

I backed the world up with a plain file copy of default.db. SQLite was in WAL mode, so the
committed rows lived in the -wal sidecar, which I did not copy. Both default.db and the .withlod
"backup" are 8192 bytes containing ZERO tables. The FarLodTest world DB is therefore EMPTY, and
the backup never held anything.

This does NOT affect the falsification result above: both runs happened before the restore
attempt, and their screenshots, far_chunks/far_instances counters and row counts are archived.
It DOES mean the fixture must be rebuilt before anyone re-runs this test: boot FarLodTest, place
the 5 rooms via POST /api/structure/build, save, and confirm chunk_lod_blobs is non-empty.

LESSON, since this will bite again: NEVER back up or inspect a live SQLite world by copying the
.db alone. Copy .db + -wal + -shm together, or checkpoint first (PRAGMA wal_checkpoint(TRUNCATE))
with the engine stopped. A .db copied without its WAL can look valid and contain nothing.

NOTE ON THE FPS DIFFERENCE, so nobody reads it as a regression: 555 with geometry vs 639 with an
empty sky is the cost of actually DRAWING 4876 instances, not scan overhead. It is also the first
matched-ish data point for draw cost: 5 chunks / 4876 instances costs ~84 FPS at 555-639, i.e.
roughly 0.24 ms/frame -- nothing like the 300x collapse the unbounded scan caused.
