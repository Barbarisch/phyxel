F5.2 -- bodies move and collide: the CPU reference body solver (F5.2a), then its GPU port (F5.2b)
(plan F5 row "GPU simulation with voxel collision"; §6.7; risk 3)
Written 2026-11-17 BEFORE any F5.2 code.

WHAT EXISTS (survey of the engine's GPU solver, GpuParticlePhysics + solver_*.comp):
  AVBD (augmented vertex block descent; Shallot / three-avbd lineage): per tick, integrate -> contacts at the
  predicted iterate -> body colouring -> 8 iterations of {primal per colour (a 6x6 block solve per body), dual per
  constraint} -> velocity from displacement -> warm start saved by feature key -> sleep. But every body is ONE
  oriented box with SCALAR (sphere) inertia; world contacts sample 26 box points against the 1/9 m occupancy pool,
  at most 6 per body; body-body is OBB-OBB SAT on a 1 m hash grid (bodies <= ~1 m); it cannot run headless (its
  device needs a window surface) and no test runs it. Multi-voxel bodies exist only on the CPU solver (boxes).
  So F5.2 builds the lab body solver on the SAME algorithm, extended to what §6.7 asks for:
  - a body is its voxel grid (F5.1), with the FULL inertia tensor (I_world = R I_body R^T in the primal);
  - contacts are voxel-on-voxel, symmetric: the surface lattice corners of X tested against the grid of Y and the
    corners of Y against X (world = a static Y with the identity transform), so a world ridge between two body
    corners is still caught. Escape rule per point in Y's voxel frame: inside a solid cell -> the nearest face
    whose neighbour is empty (depth, normal); inside an empty cell within the 2 cm margin of a solid face neighbour
    -> a speculative contact (gap); a point with no empty face neighbour is "deep" (counted);
  - body-body broadphase on world AABBs (any size), then the voxel test; the cap is per contact pair (body-world or
    body-body): K = 8, chosen as the deepest per normal direction, then farthest-point fill (keeps the support
    polygon wide); every candidate dropped by the cap is counted, never silent;
  - the engine's constants: dt 1/60, 8 iterations, alpha 0.99, beta 1e5, gamma 0.999, penalty 1..1e10, cold
    contacts at m/dt^2, static-friction anchors, start-at-rest below 0.1 m/s, sleep 30 ticks under 0.05 m/s.
    Friction per material (the engine's table: Stone 0.8, Bricks 0.8, Wood 0.6, Glass 0.2), pair = mean.
  - a world ground option: y < 0 is solid (the lab grids end at y = 0).
  The CPU reference is double precision, Gauss-Seidel per colour in ascending body order (deterministic).

     by 5 s.

     (mu 0.8) within +- 15 %; does not tip; no vertical bounce above 5 mm.
  R5 stack: 5 boxes 4x2x4 stacked flush on the floor: after 5 s each moved <= 1 cm, all asleep.
  R6 body-body, no gravity: two 4x4x4 boxes at 1 m/s toward each other: total momentum stays 0 to 1e-6 relative

F5.2b (GPU port; its own prediction section is written after F5.2a's results, before its code):
  headless (raw-handle init, as FractureGpu); compared with the reference by the same invariants on every rig and
  by trajectories on the non-chaotic rigs (R1, R2, R4: within 1 mm). NOT bit-equality: float on the GPU vs double
  on the CPU and the colour order differ, and contact dynamics are chaotic -- F4.3's integer route does not apply
  to a solver with sqrt / normalize / 6x6 solves. Said here before the work, not after a miss.

F5.2b -- THE GPU PORT (written 2026-11-17 after F5.2a's run 2, BEFORE any F5.2b code)
WHAT: BodySimGpu (engine/*/core/voxfound/BodySimGpu.*) + shaders/voxfound_bodies.comp, headless (raw-handle init as
  FractureGpu). It loads the bodies BodySimRef::add built (grids, corners, mass properties) and the world, and runs the
  same tick, in float: integrate (one thread per body) -> world contacts (per body: its corners into the world, the
  world's surface corners in its AABB into its grid; each world corner taken once by a canonical-owner rule instead
  of a set) -> body-body contacts (per body i, every j > i whose AABB overlaps) -> the same cap (deepest per bucket,
  warm-preferring, farthest-point fill) from a per-worker candidate scratch -> per-body constraint lists (count,
  prefix, scatter, then each list sorted by key so the sums are order-independent) -> colours (Jones-Plassmann rounds,
  hashed priorities) -> 8 x {primal per colour, dual} -> hard contact (body-body pushes computed per body, then the
  world, world last) -> velocities, sleep, wake -> warm start saved in a hashed table (two halves, swapped each tick).
  Not bit-equal to the double-precision reference (said in F5.2's header, before the work): different arithmetic,
  colour order and Gauss-Seidel order.
PREDICTIONS
  G1 every F5.2a rig (R1-R8b) passes its SAME assertions on the GPU: R1 within float error of the closed form
     (<= 1e-4 m after 1 s of fall: float positions), R2-R5, R6 at 8 and 32 iterations, R7, R8, R8b.
  G2 trajectories on the non-chaotic rigs R1, R2, R4: the GPU body within 1 mm of the CPU body at every tick.
  G3 two GPU runs are bit-equal (R8b, every body, every tick sampled) -- the sorted lists make the sums
     order-independent.
  G4 no candidate-scratch overflow, no constraint overflow, 0 bodies left uncoloured, on every rig (counted).
  G5 device ms per tick on R8b (21 bodies): 0.5-3 ms, dominated by the dispatch count (colours x iterations);
     reported, not gated (the 100 -> 1,000-body cost is F5.5's exit test).
  Red first: a BodySimGpu stub whose step() returns false.
