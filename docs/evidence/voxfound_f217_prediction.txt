F2.17 -- §4.6 item 10: the face pool (region arena spans per chunk; device-local; an edit writes only its own spans)
Written 2026-11-15, BEFORE any code.

Today (measured in F2.16): the preview's faces live in ONE host-visible buffer filled by a whole memcpy, and every
revision change re-creates the cull tables (ClusterCullGpu::upload: vkDeviceWaitIdle + every buffer made again and
staged) -- after a 1 m edit the next frame spends ~9 ms (faces 0.3 + sprigs 0.1 + cluster tables ~8.6) plus the
2.5 ms CPU reassembly. The plan's row 10: "Face pool sub-allocated per block / chunk" (ChunkArenaSystem). Also owed
from F2.8: "a device-local face pool may change its draw cost".

Design:
1. FacePool (core/voxfound, headless): per chunk, three spans from ChunkArenaAllocator (graphics, the region-arena
   allocator: 768 B alignment, retire queue): its faces (8 B units), its cell clusters and its direction clusters
   (32 B units). A span has slack (count + max(count / 4, one alignment unit)). layout() places every chunk; update()
   rewrites only the changed chunks: in place when the new count fits the span, else a new span and the old one
   retired -- its cluster slots zeroed (count 0) in the same update so nothing draws the retired faces. The pool image
   IS Preview::Level (faces with gaps; cluster lists with count-0 slots), so every draw path (direct per-chunk ranges,
   shadows, the multidraw) keeps working. update() returns the dirty index ranges of the three arrays; overflowing
   the block = a full layout at 1.5x (reported).
2. RegionEdit::assemble(pv, leafTex, changed) uses it; Preview carries poolRevision + the dirty ranges of the last
   revision step.
3. Renderer ({"face_pool":bool}): the face buffer DEVICE-LOCAL, filled by copies recorded at the start of the frame
   (before the shadow pass) from a per-frame-slot staging ring, behind a barrier -- queue order makes earlier frames'
   reads finish first, so no device wait. On a one-step revision with the same pool layout: only the dirty spans of
   faces and of the cull tables (ClusterCullGpu::recordUpdate: cluster words, firsts, origin words, every slot's
   command static words), sprigs + texture table as today (small memcpy). Anything else = a full upload. Off = today's
   host-visible buffer + whole re-uploads (the A/B).
4. voxfound_cull.comp: a cluster with count 0 is never visible (the empty slots).

Red first:
- CPU FacePoolUpdatesOnlyWhatChanged: 6 synthetic chunks, 400 random count changes (shrink, grow past the slack,
  to 0, back): after each, every chunk's drawn range = its list, cluster slots = its clusters (firstFace remapped) and
  zeros elsewhere in its span, spans never overlap, unchanged chunks never move, and the PREVIOUS image with only the
  dirty ranges copied from the new one equals the new one (the partial-upload contract). Red on a stub.
- GPU ClusterCullGpu PartialUpdateEqualsAFullUpload: random cluster tables, 50 recordUpdate rounds; the culled
  commands (per-cluster and compacted, origins and counts) = a fresh upload() of the same table, every round.

Predictions (gate region Perlin s7 flora 254..257 x 0..1 x 2..5, editable, Release):
1. Exact: drawn (face, origin) sets after 50 random edits = a fresh full upload (pixels within repeat noise at
   forest_floor_open, 3D view) and the verify counts stay 0.
2. Next-frame upload after a 1 m edit: ~9 ms -> <= 0.5 ms (a few chunk spans: ~30-100 KB of faces + ~10-40 KB of
   cluster words); a 4 m edit <= 1 ms. CPU assemble 2.5 ms -> unchanged (it still copies the level image; owed).
3. Steady state, whole frame, pool (device-local) vs today's host-visible buffer, 8 pairs x 5 poses: faces read
   from VRAM instead of over PCIe in 3 passes: -0.1..-0.8 ms at the face-heavy poses (overview, top_down), 0..-0.3
   elsewhere; 0 px beyond repeat noise.
4. Memory: pool slack <= 30 % of the faces (initial layout), never more than 1.5x after 200 edits.
Stop line: if partial updates are not exact on the GPU test, no live gate until they are.
