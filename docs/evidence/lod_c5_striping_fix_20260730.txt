C5 STRIPING DEFECT — ROOT CAUSE, FIX, AND RED->GREEN PROOF
Date: 2026-07-30.  Build: Debug.  Branch: destruction-system-v2 (uncommitted).

============================================================================
ROOT CAUSE
============================================================================
ChunkRenderManager::setFacesFromLod() replaced faces[] but NEVER updated `numInstances`.
`numInstances` was assigned in exactly ONE place: the end of the fine rebuild
(ChunkRenderManager.cpp:246). The renderer draws getNumInstances() instances, so after a
coarse swap it drew the FINE mesh's count against the COARSE buffer:

  coarse faces  >  stale fine count  ->  the tail is NEVER DRAWN   => see-through stripes
  coarse faces  <  stale fine count  ->  instances past the valid data drawn from stale memory

Flat/simple terrain greedy-merges to very FEW fine faces, so it is the worst case: the unit
test's flat slab merges to 6 fine faces while its level-1 coarse mesh needs 640 — the renderer
would have drawn 6 of 640 instances, i.e. 99% of the geometry missing.

This also explains every observation recorded on 2026-07-29 that I could not previously reconcile:
  * uniform level 2 striped        -> per-chunk coarse > that chunk's merged fine count
  * uniform level 3 looked solid   -> few enough faces to fit under the stale count everywhere
  * the single-chunk mesher invariant test PASSED -> the mesher was always correct; the DRAW
    COUNT was wrong, which no mesh-level test could see.

RECONCILING THE EARLIER "INTER-CHUNK" CONCLUSION (raised by the solution-auditor):
On 2026-07-29 I concluded from HeightfieldHasNoHolesFromAboveAtEveryLevel passing that the
defect was "INTER-CHUNK, not a hole in a single chunk's mesh". That inference was WRONG, and
the way it was wrong matters. What the passing test actually proved is only "the coarse MESH
for one chunk has no holes" — it says nothing about how many of those faces get DRAWN. I
treated "not a mesh hole in one chunk" as "not a per-chunk problem", which does not follow.
The truncation is per-chunk but LOOKS inter-chunk: emitFaces iterates x -> y -> z, so cutting
the instance list at N drops a CONTIGUOUS tail in that order, i.e. whole slabs at high x. Each
affected chunk therefore loses a solid block of its geometry aligned to chunk boundaries, which
reads as banding BETWEEN chunks. The screenshots bear this out: in the reverted-build capture
the surviving geometry is chunk-aligned rectangular slabs, not ragged per-cell speckle.

============================================================================
FIX (2 lines, engine/include/graphics/ChunkRenderManager.h, setFacesFromLod)
============================================================================
    numInstances = static_cast<uint32_t>(faces.size());
    needsUpdate  = true;

Second, independent defect found and fixed while investigating
(engine/src/core/LodChunkMesh.cpp, emitFaces):
    `if (mat.empty()) continue;`  DROPPED A SOLID CELL whose material failed to resolve.
    Dropping solid geometry is never a valid coarsening. Replaced with a fallback chain
    skin -> bulk -> "Default". NOTE: this is NOT the striping cause — LodBench/LodStripe
    terrain is all full cubes; it would bite sub/micro-built structures.

============================================================================
WHAT THIS DOES *NOT* CLAIM
============================================================================
* No performance claim. This is a CORRECTNESS fix. The three prior null results stand:
  LodBench is not geometry-bound, so halving faces there changed nothing measurable.
* The coarse mesher is still UNMERGED: level 1 emits MORE faces than the greedy-merged fine
  mesh (54066 vs 30799 here; 410004 vs 250845 on LodBench). Greedy-merging the coarse mesher
  is still open, and until then low LOD levels can cost more than full detail.
* LodBench itself was NOT re-measured after the fix: the Debug build wedged on that
  380-chunk world (game loop >30 s per API command) before any capture. Open.

============================================================================
FOLLOW-UP 1 — A THIRD DEFECT, FOUND WHILE CLOSING THE AUDITOR'S GAP
============================================================================
Re-running the ORIGINAL LodBench scenario exposed an inconsistency: the debug endpoint
reported chunks_by_level {1:21, 2:359} while total_chunk_faces stayed 250845 (the FINE count).

CAUSE: POST /api/debug/lod_level rebuilt each chunk's mesh but never recorded the new level
(Application.cpp set_lod_level called setLodFaces() without setLodLevel()). RenderCoordinator::
updateChunkLod() compares wanted-vs-current and `continue`s when they match, so once the tracked
level was stale, distance-driven LOD SKIPPED EVERY CHUNK and silently did nothing -- while
chunks_by_level cheerfully reported success. Any screenshot taken in that state shows full
detail regardless of the toggle, i.e. it is worthless as evidence either way.

FIX (makes the desync unrepresentable rather than merely fixing the one caller):
  * Chunk::setLodFaces(faces, LEVEL) now takes the level and records it.
  * Chunk::rebuildFaces() sets m_lodLevel = 0 (a fine rebuild IS level 0).
  * Both call sites updated; the redundant setLodLevel() in updateChunkLod removed.
RED->GREEN: LodChunkMeshTest.LodLevelTracksTheMeshActuallyBuilt, verified RED by mutating
`m_lodLevel = level;` to `(void)level;`, deleting phyxel_tests.exe and rebuilding:
    "tracked level disagrees with the mesh just built" x3 (levels 1,2,3) -> FAILED.
Restored -> 59/59 LOD tests pass.
